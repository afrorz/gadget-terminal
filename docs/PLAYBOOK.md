# 編集プレイブック（記事の型と守るべきルール）

このファイルが「品質の定義」。記事を書くとき・チェックするときは毎回ここに戻る。

---

## 1. この媒体が勝てる場所

日本語のガジェットメディアは「大手の新製品」で飽和している。勝負するのはその外側。

| 狙う | 狙わない |
|---|---|
| 海外で報じられて日本語記事がまだ無い話 | 国内メーカーのプレスリリース転載 |
| 数字が出ている話（ベンチ、価格、出荷台数） | 「〜かもしれない」だけのリーク単体 |
| 日本から買える／買えない、が論点になる話 | セール・値引き情報 |
| 複数媒体が同時に報じた＝重要な話 | ゲームの割引、懸賞、キャンペーン |
| **クラファン発の新製品（最優先）** | 決算・訴訟・株価などの業界ニュース |

`collect.py` のスコアリングはこの表をそのまま実装したもの。ペナルティ語（deal / discount / % off など）は減点される。

---

## 2. 記事の構造（この順番で書く）

1. **タイトル** — 固有名詞と数字を必ず入れる。「〜が話題」「〜がすごい」は禁止。
   - 悪い例: 新型ミニPCが登場、ファンレスで静か
   - 良い例: MeLE Quieter HD は N150 ファンレスで 2.5 インチ HDD が入る初のQuieter
2. **kicker（リード1文）** — 「何が起きたか」を一文で言い切る。結論を隠さない。
3. **本文 300〜900字程度**
   - 最初の段落で事実を確定させる（何が・いつ・いくら）
   - `## 見出し` は 2〜4 個。スペック表は必ず表にする
   - 最後に必ず **「日本から見るとどうか」** を書く。ここが差別化の中心。
     技適、電圧、日本語対応、輸入の可否、国内価格との比較、代替品。
4. **sources** — 参照した全 URL を front matter に列挙。例外なし。

## 2.5 クラウドファンディング案件の扱い

**この媒体の主戦場。** Kickstarter・Makuake 等から拾った項目は、ダイジェストに `【クラファン】` と表示される。

書くときの追加ルール:

- **「まだ製品ではない」ことを必ず明記する。** 出資は購入ではない。遅延・未達・仕様変更は日常的に起きる
- **調達額・支援者数・締切は取得時点の値**であると書く。毎日動く
- **配送予定時期は「予定」と書く。** クラファンの納期は守られないほうが多い
- **技適・PSE・電波法**は特に重要。海外クラファン品は国内で使えないことがある
- **国内クラファン（Makuake等）は「日本語で読める」ので、この媒体の差別化にはならない。** 扱うなら、海外の類似品との比較や、なぜ日本で先に出たのかという角度を足す
- 実行者の実績（過去のプロジェクト、企業か個人か）が分かるなら書く。**判断材料として最も効く**

## 2.7 検索で見つけてもらうために

記事の質とは別に、**検索エンジンに正しく伝える**ための決まりごと。

### seo_title（必須）

`title` は記事ページの見出しで、長くてよい。**検索結果に出るのは `seo_title` のほう。**

- **全角32字以内。** Google はこれ以上を切り捨てる
- **製品名を先頭に置く**
- 日本の読者が実際に打つ語を1つ入れる（価格 / 日本 / 技適 / 発売日 / スペック）

```yaml
title: Framework Laptop 12がIntel Core Series 3とThunderbolt 4に対応、DIY版549ドルから
seo_title: Framework Laptop 12はDIY版549ドルから
```

`build.py` は**34字**を超える `seo_title` をビルド時に警告する。狙いは32字以内。

> この例文は2026-08-30まで `Framework Laptop 12がCore Series 3に対応、549ドルから`（44字）
> だった。**プレイブック自身が自分のルールを破っていて**、記事もそれを写していた。
> 製品名が長いときは、詰め込まずに検索語をひとつだけ残して切ること。

### faq（2〜4問）

`FAQPage` の構造化データとして出力され、検索結果に Q&A が展開されることがある。
ガジェット記事の定番クエリはほぼ決まっている。

- 「日本で買えますか」「技適は取得していますか」「いくらですか」「いつ発売されますか」

**本文で答えていないことをFAQに書いてはいけない。** 事実の捏造と同じ扱い。

### 何を書くかの選定にも効く

「日本語記事が無い」に加えて「**日本語で検索されそうか**」を見る。

| 強い | 弱い |
|---|---|
| 固有の製品名がある（型番・ブランド） | 「新型ミニPC」のような一般名詞 |
| 価格・発売日が確定している | 噂だけで買えない |
| 日本で使えるかが論点になる | 日本と関係が薄い市場動向 |

調査レポート・訴訟・市場シェアは検索需要が細い。書いてもよいが優先度は下げる。

## 2.8 代替品とアフィリエイト

**「面白いが今は買えない」で記事を終わらせない。** クラファン案件は出荷が数か月先で
技適も未取得のことが多い。読者が今日取れる行動を示すのが記事の仕事。

front matter の `alternatives` に、同じ用途を満たして**日本で今すぐ買える**製品を1〜2件書く。

```yaml
alternatives:
  - name: 製品名
    why: 技適取得済みで国内在庫あり。同じ用途を今日から使える。
    url: https://item.rakuten.co.jp/shopname/itemcode/
    merchant: rakuten
```

- **URLの実在を確認してから書く**
- **適切な代替品が無ければ書かない。** 無理に埋めると記事の信頼が落ちる
- `why` は「なぜ代替になるか」。スペックの羅列ではなく判断材料を書く

### merchant に書いてよいのは rakuten だけ

**「代替品（新品を買う）」の文脈で提携できているのは楽天市場のみ。**
Amazon はもしも経由で2回審査落ち（2026-08、2026-09）、再申請中。
`merchant: amazon` と書いても報酬は発生せず、素のリンクになるだけ。

- 代替品を書くなら**1件目は必ず楽天**の商品ページ（`item.rakuten.co.jp/...`）
- 2件目がメーカー直販などになる場合は **merchant を書かない**
- **楽天に転売価格や怪しい並行輸入しか無いなら、merchant を書かない。**
  報酬のために読者へ不利な店を勧めるのは本末転倒。収益リンク0本の記事があってよい

**別枠として、2026-09-01 に「mmoba買取（スマホの宅配買取）」がもしも経由で提携承認された。**
ただしこれは「新品を買う」代替品ではなく「使わなくなった端末を売る」買取サービスなので、
`alternatives` の枠組みにはそのまま乗らない。**機種変更・買い替えが話題になる記事で
自然に触れられる場合だけ**使う。無理に毎回入れる筋のものではない。
front matter への正式な差し込み方（`merchant: mmoba` を通すかどうか）は、
実際に使いたい記事が出てから `checklinks.py` に追加する。

`python scripts/checklinks.py` が公開前の門番。未提携の merchant を検出して落とす。

> **なぜこの節が厳しいか。** 2026-08-16〜28 の46記事で、代替品リンク20本すべてが
> `merchant: amazon` だった。当時のルールが「**2件書くときは**うち1件を楽天に」という
> 条件つきで、実際には毎回1件しか書かなかったため一度も発火しなかった。
> build.py も未提携の merchant を黙って素通ししていたので、12日間ゼロ円のまま
> どこにも警告が出なかった。**記事は正しく積み上がっているのに収益だけがゼロ**という
> 壊れ方は目で気づけない。条件つきのルールを書かないこと。

### アフィリエイトについて

リンクは `config/site.yaml` の `site.affiliate` 設定でもしもアフィリエイト経由に変換される。
**`enabled: false` のあいだは素のURLのまま**で、代替品セクション自体は出る。
編集上の価値はリンクの種類と無関係なので、収益化の有無にかかわらず書く。

**景品表示法（ステマ規制）への対応はコード側で強制している。** アフィリエイトリンクが
1つでもある記事には、本文冒頭に「この記事にはアフィリエイト広告を含みます」が自動で入り、
代替品の見出しにも「広告」ラベルが付く。人間の判断に委ねると漏れるため、書き手が意識する
必要はない。**逆に、この表示を消す改修をしてはいけない。**

## 2.9 特集ページ（content/features/）

**特集だけは「海外の、まだ日本語で読めない話」の縛りを外している。**（2026-09-01 決定）

日々のニュース記事は「まだ日本語記事が無い話」を追う。これは変えない。
一方で特集ページは**「すぐ欲しい」と思って読む人のためのページ**なので、
そこに買えないものしか並んでいないと役に立たない。
**国内で普通に買える製品を載せてよい。**

### 外した縛りの代わりに、必ず守ること

**載せる製品には入手性の判定を必ず付ける。** これが特集ページの存在理由。
ここを外すと「白いガジェット10選」と同じになり、誰でも書けるページに落ちる。
**技適まで踏み込んで買える／買えないを言い切るのが、この媒体が持っている差分。**

載せてよいのは次を満たすものだけ。

1. **メーカー公式か、日本の正規代理店が国内販売している**こと
2. **技適の状況を一次ソースで確認できた**こと（`source:` にそのURLを書く）
3. **転売価格ではない**こと。公式価格から大きく乖離した出品しか無いなら載せない

`availability` は3つから選ぶ。判定が無い製品はビルド時に警告が出る。

| 値 | 意味 |
|---|---|
| `verified` | 国内正規流通＋技適を一次ソースで確認できた |
| `official` | メーカー公式が日本発送しており、技適取得を公式に明記している |
| `caution` | 買えるが注意点がある（対象モデル限定など） |

### 記事として上から読ませる

**横並びのカードにしない。** 並べると比較表になり、読み物ではなく一覧になる。
1製品ずつ縦に積み、次の順で組む。

```
通し番号＋ブランド → 製品名 → 判定バッジ → 大きな写真 → 本文 → 事実の箱 → リンク
```

- **本文（`note`）が記事の実体。** 1製品あたり3段落・300〜400字を目安に書く。
  空行で段落が割れる。`**強調**` が使える
- 価格・買えるところ・技適は本文の後ろに箱でまとめる。**本文に混ぜない**。
  読ませたいのは判断の理由で、数字は確認用だから
- 写真は原寸比のまま幅いっぱいに出す。切り抜かない

### 写真は必須

**ガジェットの特集で写真が無い製品カードは公開しない。** `image:` が空の製品は
ビルド時に警告が出る。読者は写真で興味を持つので、ここを落とすとページごと死ぬ。

- 引用元は PLAYBOOK 3.5 と同じ（**メーカー公式・正規代理店・クラファンページのみ**）
- `credit:` を必ず書く。カードの右下に出典として出る
- **1枚ずつ開いて目視する。** 店舗のトップページから取ると他製品や
  キャンペーンのバナーが混じる。実際 Keychron では「Keychron Ultra
  リニア磁気スイッチ」の仕様バナーが候補に出てきた（K1/K2/K8 の写真ですらない）
- 縦長のマーケティング画像（1920×6769 など）はカードに使えない。
  製品紹介記事側に 1280×720 程度の実物写真があることが多い

### 「今回入れなかったもの」を必ず書く

条件を満たさなかった製品は `excluded:` に理由つきで残す。
**「載っていない＝悪い製品」ではなく「確認が取れなかった」**という区別を読者に見せる。
ここが他のまとめ記事との差になる。**確認できないものを「買える」と書かない。**

> **なぜ技適を正規流通で代替してよいか。** 技適のない無線機を日本国内で販売するのは
> 違法なので、正規流通に乗っている時点で取得しているとみなせる。罠は**並行輸入品と
> マーケットプレイスの出品**で、Amazonに出ているだけでは安全の根拠にならない。
> なお型番は認証申請時と店頭表記が食い違うことが多く、総務省のデータベースを
> 型番で引いて出てこなくても「技適なし」とは断定できない。断定しないこと。

## 3. 絶対に破らないルール

- **元記事に無い数字を書かない。** 推測値を書くなら「未発表」「編集部推定」と明記する。
- **リークは必ずリークと書く。** 「〜とされる」「リーク情報のため確度は中程度」。
- **翻訳ではなく再構成。** 元記事の文をそのまま訳して並べない。事実を抜き出し、日本の読者向けに組み直す。引用は最小限＋出典明記。
- **画像をダウンロードして自社サーバーに置かない。** 公式サイトの画像は「3.5 画像をどう用意するか」の条件でホットリンク引用してよいが、**他のニュースサイトの画像は引用元が公式でないため使わない。**
- **円換算は書かない。** 為替で陳腐化するのでドル・ユーロのまま。必要なら「為替次第で〜円前後」と幅で。
- **在庫・購入リンクは「掲載時点」と明記。**
- **一社の報道しかない話は、その旨を書く。**

## 3.5 画像をどう用意するか

**ガジェットメディアで実物が見えないのは弱い。** ただし転載はしない。使える手は3つ。

| 手段 | 書き方 | 一覧カードへの反映 |
|---|---|---|
| **YouTube動画を埋め込む（推奨）** | front matter の `embeds` に `type: youtube` と `id` | **サムネイルが自動でカード画像になる** |
| **公式サイトの製品画像を引用する** | front matter に `thumbnail:` と `thumbnail_credit:` | そのまま使われる |
| **自社の写真・許諾済み素材** | front matter に `thumbnail: /assets/xxx.jpg` | そのまま使われる |
| 何も無い場合 | 何も書かない | 自動生成のアイキャッチ |

### 公式サイトの画像を引用するときの条件

**引用元は「公式」に限る。** 具体的には次のみ。

- メーカーの公式製品ページ、公式プレスルーム
- クラウドファンディングのプロジェクトページ（Kickstarter / Indiegogo / Makuake 等）

**他のニュースサイトが撮った写真・加工した画像は使わない。** それは転載になる。

守ること:

1. **画像URLを直接参照する（ホットリンク）。ダウンロードして `public/` に置かない。**
   自社サーバーに複製を作らないことで、複製にあたる行為を避ける
2. **`thumbnail_credit` に出典を必ず書く。** 記事下に「出典: ◯◯」として表示される
3. `sources` にも当該ページのURLを入れる
4. 画像に埋め込まれた透かし・他媒体のロゴが入っているものは使わない（公式素材ではない証拠）
5. 人物が主題の画像は避ける（肖像の問題が別に発生する）

```yaml
thumbnail: https://example-maker.com/press/product-hero.jpg
thumbnail_credit: Example Maker 公式製品ページ
```

**注意:** 公式サイトの画像にも著作権はある。この運用は「引用（出典明示・主従関係・必要な範囲）」の枠内で使う前提であって、
権利者が明示的に禁じている場合や、画像そのものを主目的に見せる使い方は範囲外。
プレスキットに利用条件が書かれている場合はそれに従う。削除依頼が来たら速やかに外す。

### 動画IDは必ず存在確認する

存在しないIDを書くと空白の枠が出るだけになる。次をWebFetchして `title` と `author_name` が返ることを確認してから書く。

```
https://www.youtube.com/oembed?url=https%3A//www.youtube.com/watch%3Fv%3D<動画ID>&format=json
```

### 別製品の動画を貼らない

「同じシリーズの前世代」は別製品。読者を誤解させるので使わない。**該当する動画が無ければ、無いままでよい。**

## 4. スコアと採否の目安

| スコア | 扱い |
|---|---|
| 12pt 以上 | その日の主役。掘り下げて書く |
| 6〜11pt | 通常記事 |
| 1〜5pt | 短報、またはまとめ記事の1項目 |
| 0pt 以下 | 書かない |

複数媒体が報じている（`also_covered_by` あり）ものは、他媒体側も必ず読んでから書く。片方にしかない数字が拾える。

## 5. 1日の流れ（半自動運用）

```
朝  python3 scripts/collect.py --top 30     → data/digest/YYYY-MM-DD.md
    ダイジェストを開き、書くものに [x] を付ける（3〜5本）
    Claude に「このダイジェストの ◯番を記事にして」と渡す
    content/posts/ に下書きが出るのでレビュー（事実・数字・日本視点）
    python3 scripts/build.py                → public/
    git push                                → 公開
```

レビューで見るのは3点だけ。**数字が元記事と一致しているか / リークがリークと書かれているか / 日本視点のセクションが具体的か。**

## 6. 公開後

- 検索流入が付くまで 2〜3 か月。最初の 30 本は「本数を出す」ことを優先する。
- **記事30本を超えたら PR TIMES のメディアユーザー登録を申請する。** 文面は `docs/PRTIMES申請.md` に用意済み。
  通れば製品画像を正規に入手できるようになり、画像不足が構造的に解消する。
- 同じテーマで 3 本たまったら、まとめ記事（比較・年表）を作る。まとめ記事のほうが検索で強い。
- 収益化を入れるのは記事 30 本＋月間 PV が動き出してから。それまでは `site.yaml` の `affiliate.enabled` は false のまま。
